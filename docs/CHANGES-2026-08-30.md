# Livraison KeltiaWave du 30 août 2026

## Library et administration

- La source `Internet` est disponible lors de la création d'une phrase. Une URL
  HTTP(S) devient alors obligatoire et est conservée dans `phrases.source_url`.
- La matrice des voix validées affiche la source Internet sous forme de lien
  externe. Les colonnes `Signal` et `Niveau` ont été compactées, le libellé
  `Niveau d'accent` est devenu `Niveau` et une valeur absente est affichée `NA`.
- La validation effectuée dans l'administration crée ou actualise la décision de
  validation utilisée par la bibliothèque publique : un audio approuvé apparaît
  donc dans les voix validées.
- La fenêtre de modification d'un enregistrement possède une zone défilante et
  des actions toujours visibles. Elle expose les listes prédéfinies et les
  valeurs personnalisées pour le domaine, la source, le niveau de phrase, la
  région/pays, la ville, l'accent, le niveau et le nom du locuteur.
- Les anciennes métadonnées personnalisées restent éditables grâce aux choix
  `Autre domaine`, `Autre source` et `Autre région / pays`.
- L'import administrateur accepte un fichier de métadonnées et une archive
  d'audios MP3 pour charger un jeu de données avec phrase, traduction et
  informations de provenance et de locuteur.

## Navigation et portail

- Le logo de Library/Komz renvoie vers le portail correspondant à
  l'environnement : `127.0.0.1:4100` en local, `staging.keltiawave.com` sur le
  staging et `keltiawave.com` en production.
- Le personnage surfeur de la page d'accueil utilise maintenant un PNG RGBA avec
  une véritable transparence, sans damier intégré.

## Compatibilité des données

Au démarrage, le backend ajoute la colonne nullable `source_url` à la table
`phrases` si elle n'existe pas. Les enregistrements existants restent valides et
les champs absents restent facultatifs, hors URL lorsque la source sélectionnée
est `Internet` dans l'interface.

## Vérifications de livraison

```bash
cd apps/corpus
npm run build

cd ../..
python -m pytest backend/tests
```

Le staging est ensuite construit depuis la révision Git livrée avec :

```bash
SSH_TARGET=ubuntu@vps-dc75d8a6.vps.ovh.net \
  ./scripts/deploy-staging-ovh.sh --apply
```

Lors d'un clonage staging vers une candidate de production, les applications
frontend sont redémarrées après la recréation du backend. Elles renouvellent
ainsi sa résolution DNS Docker avant les tests fonctionnels, ce qui évite une
réponse `502` liée à l'ancienne adresse du conteneur.
